# Solply 프로덕트 설계

> **Solply — Settle On Ledger, for supply.**
> 본사-가맹점 사이 식자재 대금(물대)의 청구·검증·협상·결제·정산을 AI 에이전트들이 사람 개입 없이 온체인에서 끝낸다.
> 이름의 뜻: SOL + Supply(납품) 합성 + "SOL = Settle On Ledger" 백로님 태그라인.

## 1. 문제

프랜차이즈 본사와 가맹점 사이 식자재 거래는 발주 → 납품 → **외상** → 주/월 정산 구조.

- **미수금 관리**: 가맹점 매출은 변동이 큰데 물대는 정기 청구 — 본사 경리팀이 연체 관리에 인력 소모
- **검수 분쟁**: 발주량-납품량 불일치, 품질 문제로 인한 차감 정산 다툼이 일상
- **정산 불신**: 가맹점은 본사의 정산 내역을 검증할 수 없음 — 본사-가맹점 갈등의 뿌리

## 2. 솔루션 (에이전트 구성)

### 본사 정산 에이전트 (HQ Agent) — 1대
- 납품 완료 이벤트 수신 → 가맹점별 청구서 자동 생성·발송 (A2A + x402)
- 가맹점 에이전트의 차감/유예/분할 제안을 **정책 + 온체인 신용 이력** 기반으로 심사
- 수금 확인 → 정산 기록 → 미수금 대시보드 갱신
- 신용점수 기반 외상 한도 동적 조정

### 가맹점 에이전트 (Store Agent) — N대 (같은 코드, 지점별 정책/지갑만 다름)
- 청구서 수신 → **자체 검수 데이터와 대조 검증** → 불일치 시 차감 재청구 제안
- POS 매출·지갑 잔액 기반 지불 판단:
  - 여유 → 즉시 USDC 결제 (사람 개입 0)
  - 부족 → "금요일 카드정산금 입금 시 납부" 유예 제안 or 분할 제안
- 이상 청구(평소 대비 급증, 미발주 품목) → **결제 거부 + 사람 에스컬레이션**
- 합의된 예약 → 예약일에 자동 실행

### 가맹점 간 직거래 (Store-to-Store) — 신규 아이디어 (7/27)

지금은 본사↔가맹점 세로 소통뿐인데, **가맹점 에이전트끼리 가로로 협상하는 구조**를 추가한다.
**구현 설계는 [store-to-store-design.md](store-to-store-design.md)** — 도구·데이터·데모 대본·완료 기준까지 있다.

- **상황**: A지점은 재고 잉여(예: 냉장 닭 과잉), B지점은 재고 소진으로 본사에 긴급 발주 직전
- **플로우**: B 에이전트가 발주 전에 인근 지점의 잉여 재고를 조회 → A 에이전트와 수량·가격 협상 → 합의 시 **본사가 아니라 A에게 공급받고, 대금은 B → A로 온체인 USDC 결제**
- **본사의 역할**: 거래를 승인·기록하는 심판. 프랜차이즈 특성상 품질·위생 책임이 있으므로 HQ 에이전트가 거래를 승인(또는 거부)하는 단계를 넣는다 — 기존 "자율성 + 통제" 서사가 P2P 거래에도 그대로 확장된다. 거래 내역은 본사 장부에도 기록되어 "같은 장부" 논거 유지.
- **가치**: A는 폐기 손실 감소, B는 긴급 발주 리드타임 단축, 본사는 물류비 절감
- **심사 포인트**: 트랙 C "Multi-Agent Commerce — 에이전트 간 A2A/A2B 협상·주문·결제"에 정면으로 부합. 기존 시나리오가 트랙 A/B를 커버하므로, 이것이 들어가면 세 트랙을 한 프로덕트로 관통한다.

💭 구현 관점: 가맹점 에이전트는 이미 같은 코드에 지갑·정책만 다르므로, 재고 조회 도구 + 지점 간 x402 왕복만 추가하면 결제 레일은 전부 재사용된다. `fixtures.json`에 지점별 재고 데이터만 심으면 시나리오가 성립한다.

### 자율성 + 통제 (심사 핵심)
- 건당 자동결제 한도(`AGENT_SPEND_LIMIT_USDC`), 초과 시 사람 승인
- 유예는 납부기한 내 + 청구액의 X% 미만만 자동 수락, 분할은 2회까지
- 모든 판단은 실행 로그로 기록 (심사 기준 4번: 실행 증빙)

## 3. 아키텍처 (GCP + Solana)

```

        │                      │
   BigQuery ◀── 정산 이력 ──── explorer 링크
        │
   대시보드 (Cloud Run) — 미수금 현황·신용점수·라이브 tx 로그

```

- **Gemini/ADK**: 에이전트 두뇌 (청구 판단, 검수 대조, 협상 심사) — 심사 기준 2
- **A2A + x402 extension**: 에이전트 간 결제 요청/협상 메시지 — 심사 기준 3
- **Pub/Sub + Eventarc + Workflows**: 주최측 권장 비동기 파이프라인 그대로
- **Cloud Scheduler + Run Jobs**: 유예/분할 예약 실행
- **Firestore**: 상태, **BigQuery**: 정산 이력 → 대시보드

## 4. 데모 시나리오 (3분, 가맹점 3곳)

1. **A지점** — 납품 → 검수 일치 → 즉시 자동 결제 (정상 플로우)
2. **B지점** — 검수 불일치(닭 5마리 부족) → 에이전트 간 차감 협상 → 조정 결제 ⭐
3. **C지점** — 매출 부진 → 유예 제안 → HQ가 신용 이력 보고 수락 → 예약 체결 → 예약 실행 tx ⭐
4. 피날레 — 온체인 정산 대시보드 + explorer 링크. "본사 경리팀과 사장님의 새벽 정산이 에이전트 4대로 대체됐습니다"

+숨긴 카드: 이상 청구(미발주 품목) 주입 → 가맹점 에이전트가 결제 거부하는 장면
+신규 후보 (7/27): **가맹점 간 직거래** — A지점 잉여 재고를 B지점이 P2P 협상으로 넘겨받고 B→A 온체인 결제 (§2 참고, 채택 시 시나리오 E)
