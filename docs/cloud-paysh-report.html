02

이틀 동안 무슨 일이 있었나

실제 작업 순서 그대로.

  • 7/29 밤 · 집

    구글 클라우드 첫 연결과 첫 배포

    프로젝트에 Cloud SQL·Secret Manager·Cloud Run 서비스 2개(공개 API + 비공개 결제)와 데모 Job을 만들고 첫 배포. 데브넷 지갑 4개를 만들어 열쇠를 Secret Manager에 올렸다.

  • 첫 함정: 빌드팩이 만든 죽은 리비전 rev 00003

    backend/에서 배포하니 빌드팩(소스를 보고 이미지를 알아서 만들어주는 도구)이 서버 시작 방법을 잘못 추측해 기동 실패. 저장소 루트에 Dockerfile을 직접 두는 방식으로 정착 — 시작 명령을 우리가 명시한다.

  • 7/30 오전 · 회사

    회사 맥에 gcloud 환경 복제

    SDK 설치(~/.local/google-cloud-sdk) → 로그인 2종(CLI용 + 애플리케이션 기본 자격증명, Vertex AI가 쓴다) → Secret Manager에서 지갑 4개 내려받아 집 지갑과 동일함을 확인. 이제 양쪽 맥 어디서든 배포 가능.

  • 경제 루프 라이브 가동 rev 00005

    판매→카드정산→조달→재입고→예약납부가 한 바퀴 도는 틱을 배포하고 Cloud Scheduler가 10분마다 굴리게 걸었다. 라이브 URL이 "과거 데모의 기록"이 아니라 "지금 거래 중인 시스템"이 됐다. 비용도 점검: Vertex 하루 $0.05~0.15, Cloud SQL 월 $8~10 — 8/21까지 다 합쳐도 $15 안쪽, 크레딧 $300의 5%.

  • 손님 페이지(/shop) 배포 실패 rev 00006

    배포 명령에 --clear-base-image가 빠지자 서비스에 남아있던 빌드팩 설정이 되살아나 Dockerfile을 무시하고 잘못된 시작 명령으로 빌드 → 기동 실패. Cloud Run은 새 버전이 못 일어나면 트래픽을 안 넘긴다 — 그래서 라이브는 무사했다.

  • /shop 재배포 성공 + 라이브 구매 검증 rev 00007

    올바른 명령으로 재배포. 라이브에서 실제 구매 1건(닭 1개 → 재고 20, 매출 0.5 USDC 적립)까지 확인. 이제 방문자 구매가 라이브 경제의 진짜 수요가 된다.

  • pay.sh 연동 rev 00008 → 00009 → 00010

    이 문서의 후반부 전체가 이 이야기다 — 조사, 스파이크, 구현, 그리고 컨테이너에서 두 번 조용히 죽은 것을 잡아낸 과정. 최종적으로 09:40:58에 라이브 에이전트가 시세를 사고 그 데이터로 직거래를 제안하는 것까지 확인.

03

배포는 어떻게 이루어지나

명령 한 줄 뒤에서 벌어지는 일 — 그리고 왜 --clear-base-image가 생명줄인지.

gcloud run deploy solply-api --source . --clear-base-image --region us-central1  # 반드시 저장소 루트에서
① 소스 압축·업로드.gcloudignore가 문서·테스트·비밀 파일을 제외
→
② Cloud Build루트 Dockerfile로 이미지 빌드 — 파이썬 + 프론트 + pay CLI
→
③ Artifact Registry완성된 이미지를 저장
→
④ 새 리비전 생성rev 00010 같은 번호가 붙은 불변 배포 단위
→
⑤ 기동 확인8080 포트를 열고 살아나는지 검사
→
⑥ 트래픽 100% 전환실패하면 전환 없음 — 이전 버전이 계속 서빙

함정의 정체: --source . 배포는 원래 Dockerfile을 쓰지만, 서비스에 빌드팩 설정이 한 번이라도 남으면 그게 우선한다. 빌드팩은 시작 명령을 uvicorn app:app으로 추측하는데 실제는 app.main:app — 그래서 ⑤에서 죽는다. --clear-base-image가 그 설정을 지워 Dockerfile로 되돌린다. 이틀 연속(리비전 00003, 00006) 같은 함정에 빠졌고, 이제 배포 절차에 박제됐다.

04

pay.sh — 왜 넣었고, 뭐 하는 물건인가

심사 기준 3의 마지막 퍼즐 조각.

왜 — 심사 기준 3은 "USDC · x402 · pay.sh를 실제 유스케이스에 녹였는가"를 본다. 우리는 USDC(정산 통화)와 x402(정산 프로토콜)는 처음부터 실사용이었지만 pay.sh만 비어 있었고, 인수인계 문서에 "정직한 약점 ②"로 적어뒀었다.

무엇 — pay.sh는 솔라나 재단 + 구글 클라우드가 만든 에이전트 전용 API 결제 도구다. 방향이 중요하다: 우리가 대금을 받는 레일이 아니라, 에이전트가 남의 유료 API를 쓰고 그 자리에서 USDC로 지불하는 레일. 사람처럼 회원가입·카드등록·API 키 발급을 못 하는 에이전트를 위해, HTTP 402(Payment Required) 챌린지를 자동으로 지불하고 통과시켜 준다.

어디에 — 지점 에이전트가 조달 경로(지점 간 직거래 vs 본사 발주)를 고르는 find_supply 판단 직전. 모든 조달이 이 길목을 지나므로, 조달이 일어날 때마다 "판단 재료를 돈 주고 사는" 장면이 라이브에서 반복된다. 지금까지 에이전트는 물건값만 냈는데, 이제 정보값도 자기 지갑으로 낸다 — "판단 재료도 공짜가 아니다."

한 번의 시세 구매에서 벌어지는 일 (x402 자동 결제)

에이전트가 pay --sandbox curl https://debugger.pay.sh/mpp/quote/CHK 를 실행하면:

1에이전트 → 시세 API그냥 GET 요청을 보낸다
2시세 API → 에이전트402 Payment Required — "돈 내면 줄게" + 결제 조건
3pay CLI샌드박스 지갑에서 USDC를 자동 지불 (첫 호출이면 지갑도 자동 생성·충전)
4에이전트 → 시세 API지불 증명을 붙여 재요청
5시세 API → 에이전트200 OK + 시세 JSON + payment-receipt 헤더 (온체인 트랜잭션 참조가 든 영수증)

우리가 본사↔지점 정산에 직접 구현한 그 x402 왕복을, pay.sh는 데이터 구매 쪽에서 기성품으로 해주는 것이다. 영수증의 온체인 참조는 market.quote_purchased 이벤트에 저장돼 심사 기준 4(실행 증빙)와도 연결된다.

05

연동 과정 — step by step

조사부터 라이브 검증까지, 실제 진행 순서 그대로.

1단계 — 정체 확인과 스파이크 (될지부터 확인)

미뤄뒀던 이유가 "데브넷 지원 불확실"이었으니, 코드를 쓰기 전에 실제로 되는지부터 확인했다.

brew install pay          # 홈브루 정식 패키지 (0.24.0)
pay --sandbox curl -s https://debugger.pay.sh/mpp/quote/AAPL
{"symbol":"AAPL","price":"127.89","currency":"USD","source":"mpp-demo"}  # 402를 스스로 지불하고 통과!
  • --sandbox가 핵심: 연습용 체인(Surfpool)에 연결하고 임시 지갑을 자동 생성·충전해준다 — 실자금 0원
  • -si로 헤더를 열어보니 payment-receipt에 온체인 트랜잭션 참조가 들어 있었다 — 증빙 확보 가능
  • 설정 파일이 전혀 없는 새 환경(컨테이너 조건)에서도 도는지 가짜 HOME으로 미리 확인 — 통과
  • 호출당 약 4.5초 — 10분 캐시를 붙이면 틱 지연으로 무시할 수준

2단계 — 꽂을 자리 선정

"산 데이터가 실제로 판단에 쓰여야" 이야기가 성립한다. 조달 그래프에서 모든 경로가 지나는 길목이 find_supply 노드다:

check_stock재고 점검 — 안전선 미달이 조달의 방아쇠
→
find_supply⭐ 여기서 시세를 pay.sh로 구매 → 본사 발주 vs 지점 잉여 비교
→
propose_trade잉여 지점에 직거래 제안
or
본사 발주납품·청구 발행 → x402 정산

직거래로 가든 본사 발주로 가든 시세 구매를 반드시 지나므로, 라이브 경제가 도는 한 이 장면이 계속 재생된다.

4단계 — 컨테이너에서 두 번 조용히 죽다

로컬 맥에서는 완벽했는데, 배포하니 시세 구매 이벤트가 없었다. 실패해도 조달은 계속 가게 설계했기 때문에 겉으로는 아무 문제가 없어 보였다 — 조용한 실패의 대가다.

06
