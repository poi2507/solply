## 2026-07-25: 트랙 및 도메인 확정 과정

### 트랙: A (Agent-Initiated Commerce)
- 트랙 A = 에이전트가 **결제의 시작점**: 청구서 생성 → 입금 추적 → 정산까지 풀사이클
- "경리 업무를 AI가 온체인 위에서 돌리는 것"이 완성형 문장
- 해커톤은 공식 단일 트랙이라 B(자율 지불)/C(에이전트 간 결제) 요소를 섞어도 무방

### 아이디어 논의 과정 (전체 흐름)

1. **공모전 요구사항 해석부터 시작** — "추천만 하는 챗봇을 넘어, 스스로 판단하고 결제·정산까지 실행하는 에이전트". 두 조건이 핵심: ① 매 단계 사람 승인 없이(자율성) ② 정해진 한도 내에서(통제). 심사에서 제일 확실한 당락 포인트는 "시연 중 실제 devnet 트랜잭션 발생 + 실행 로그 증빙"으로 판단.

2. **트랙 A 선택 (사용자)** → "Initiated"의 의미를 정리: 결제를 사람이 시작하는 게 아니라 **에이전트가 시작**. 청구 → 수금 확인 → 정산의 3단계 풀사이클. "경리 담당자를 AI로 대체"가 완성형 문장.

3. **"도메인을 좁히면 어필될까?" (사용자)** — 결론: 좁히는 건 무조건 유리 (심사 기준 1번이 "기존 문제를 어떻게 해결했는지"). 사용자가 패션 제안 → "AI가 옷을 사줌" 각도는 기각 (왜 온체인?에 답 없음), "패션의 정산 문제" 각도로 전환 → 공구 정산 아이디어 도출.

4. **공구 정산을 상세 디벨롭**했으나 사용자가 공구 도메인을 모름 → 기각. 교훈: **도메인은 본인이 잘 알거나 빠르게 배울 수 있는 것** (파이널리스트 Q&A에서 도메인 무지가 드러나면 치명적).

5. **공과금 대납 아이디어 (사용자)** — "가스비 문자가 트리거 → 에이전트가 판단 → 결제". 트리거 기반 구동 구조는 우수해서 채택. 단 두 가지 문제: ① 이건 트랙 B 모양 (지불하는 쪽) ② "가스공사가 USDC 받나?" → 셰어하우스 N빵으로 비틀어 트랙 A 구조 복원.

6. **와우 팩터 논의 (사용자: "범위가 좁게 느껴져, 심사위원 마음을 사로잡기 어려울 듯")** — 진단: 좁은 게 문제가 아니라 와우 모먼트가 약한 것. 해법: 룸메이트마다 자기 에이전트를 두는 멀티 에이전트 구조로 업그레이드 → "사람 손 없이 에이전트 4대가 서로 통신하며 정산을 끝내는" 장면 + "이상 청구를 에이전트가 거부"하는 장면.

7. **협상 플로우 추가 (사용자)** — "돈이 없으면? 에이전트가 수입 일정 보고 납부 예약을 제안하거나 분할납부 신청, 상대 에이전트가 금액 합당성을 판단해서 수락" → 단순 자동화를 넘어 **에이전트 간 협상**으로 격상. 온체인 납부 이력 = 신용점수 개념도 여기서 파생. 스코프 가드레일(필수/여유/버림)도 이때 확정.

8. **포장지 교체 요구 (사용자: "셰어하우스가 맘에 안 들어, 기술은 그대로 두고 포장을 바꾸자")** — SaaS 구독 정산 / 글로벌 팀 정산 / AI 에이전트 회사 3안 제시 → 사용자: "너무 범용적, 더 디테일하게" → **사용자가 프랜차이즈 식자재 방향 제안** → 미수금·검수 분쟁·정산 불신이라는 구체적 문제에 아키텍처가 완벽 매핑됨을 확인 → **확정**.

9. **이름 논의** — Solomon 등 제안 → 사용자의 날카로운 지적: "다른 사람이 AI한테 물어봐도 같은 이름 나오는 거 아냐?" → 맞음. 유니크함은 아이디어의 구체성에서 나옴. 도메인 확정 후 물대장 등 제안했으나 기각 → **사용자가 직접 고민하기로**.

### 도메인 탐색 여정 (기각 사유 포함)

| 후보 | 기각/채택 사유 |
|---|---|
| 패션 쇼핑 대행 | ❌ "왜 온체인?"에 답 없음 (옷은 카드로 사면 됨), 에이전틱 쇼핑 데모는 흔함 |
| 패션 공구(공동구매) 정산 | ❌ 아이디어 자체는 좋았으나 사용자가 공구 도메인을 모름 → Q&A 리스크 |
| 공과금 대납 (문자 트리거) | ❌ 사용자 제안. 트리거 구조는 채택했으나 "가스공사가 USDC 받나?" 문제 |
| 셰어하우스 공과금 N빵 | ❌ 아키텍처는 완성됐으나 포장이 좁고 와우 팩터 부족하다고 판단 |
| SaaS 구독 정산 / 글로벌 팀 정산 / AI 에이전트 회사 | ❌ 사용자: "너무 범용적, 더 디테일했으면" |
| **프랜차이즈 식자재(물대) 정산** | ✅ 사용자 제안. 디테일 있는 실제 B2B 문제 + 아키텍처 완벽 매핑 |

### 살아남은 핵심 설계 자산 (도메인 바뀌어도 유지된 것)
1. **트리거 기반 구동**: 이벤트(납품 완료) → 에이전트 판단 → 실행
2. **멀티 에이전트**: 청구하는 에이전트 ↔ 지불하는 에이전트들 (A2A/x402)
3. **이상 감지 → 결제 거부 → 사람 에스컬레이션** (자율성+통제의 증명)
4. **협상 플로우** (사용자 아이디어): 잔액 부족 시 유예/분할 제안 → 상대 에이전트가 정책+신용 이력으로 심사 → 합의 → 예약 실행 (Cloud Scheduler)
5. **온체인 납부 이력 = 신용점수** → 외상 한도 동적 조정
6. **좁은 데모 + 큰 비전** 프레이밍: "반복 청구·정산이 있는 모든 B2B에 적용되는 정산 레이어"

### 심사 대응 논리 (확정)
- **왜 AI 에이전트?** 검수 대조·미납 관리·협상은 "판단이 필요한 반복 노동"
- **왜 온체인?** ① B2B 외상(어음, 30~60일 정산)을 즉시 정산으로 ② 조작 불가능한 납부 이력 = 신용 ③ 본사-가맹점 정산 투명성 (사회적 공감대 있는 갈등)
- **와우 모먼트**: 사람 손 없이 에이전트 4대가 청구·협상·결제·정산 / 검수 불일치 자동 조정 / 이상 청구 거부

## 2026-07-26: 프로젝트명 확정 — **Solply**

- **Solply = SOL + Supply(납품)** + 태그라인 "SOL = Settle On Ledger, for supply"
- 이름 요구사항의 진화: 재치 → 유니크함(남들이 AI에게 물어도 안 나올 것) → 주제(식자재/정산)가 담길 것 → **Solana의 의미가 섞일 것**
- 크립토/솔라나 생태계 충돌 검색 통과 (Solvent는 3중 충돌로 기각)
- 기각된 후보 (재제안 금지): Solomon, 돈돈, 알페이, PayGent, PayPilot, 물대장, 본가, 새벽정산, 정산이, Settler, Settly, Billow, 맑음, 장보고, 마감, 단골, 식비서, SolBooks, 솔맛
