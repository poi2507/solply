02에이전트 설계

가맹점 에이전트는 동일한 코드에 지갑·정책·검수 데이터만 다르게 주입한 인스턴스다. 모든 도구 호출은 events 로그에 남아 심사 기준 4번(실행 증빙)의 근거가 된다.

본사 정산 에이전트HQ · 1대

돈을 받는 쪽. 청구를 시작하고, 제안을 심사하고, 수금을 검증한다.

  • create_invoices()납품 이벤트 → 가맹점별 청구서 생성 (품목·수량·단가)
  • send_payment_request()A2A + x402로 가맹점 에이전트에 결제 요청 전송
  • review_proposal()차감·유예·분할 제안을 정책 + 신용 이력으로 심사 ← Gemini 판단 핵심
  • verify_payment()온체인 트랜잭션 조회로 수금 검증 (금액·memo 대조)
  • record_settlement()정산 확정, 영수증 발행, BigQuery 기록
  • adjust_credit_limit()납부 이력 기반 외상 한도 동적 조정
가맹점 에이전트STORE · ×3

돈을 내는 쪽. 검증 없이 내지 않고, 못 낼 때는 협상한다.

  • verify_delivery()청구서 ↔ 자체 검수 기록 대조, 불일치 항목 산출
  • assess_cashflow()지갑 잔액 + POS 매출 흐름으로 지불 여력 판단 ← Gemini 판단 핵심
  • execute_payment()한도 내 자율 결제 (Payments Service 호출)
  • propose_adjustment()검수 불일치분 차감 재청구 제안
  • propose_deferral()유예("금요일 카드정산금 입금 시") 또는 분할 제안
  • refuse_payment()이상 청구(미발주 품목·급증 금액) 거부 + 사람 에스컬레이션
자율성 + 통제 (심사 핵심 장치) — 건당 자동결제 한도 AGENT_SPEND_LIMIT_USDC 초과 시 사람 승인 필수 · 유예 자동 수락은 납부기한 내 + 청구액 20% 미만 · 분할은 2회까지 · 모든 판단에 사유(reasoning)를 로그로 남김.

03에이전트 간 결제 프로토콜 (A2A + x402)

HTTP 402 Payment Required의 의미론을 에이전트 통신에 확장한 x402를 A2A 확장으로 사용. "가져다 붙인" 프로토콜이 아니라 청구–지불 대화 자체가 이 프로토콜 위에서 돈다.

HQ → A2A 태스크로 payment-required 전송 — 금액(USDC), 수취 주소, memo = invoice_id, 납부기한, 품목 명세 포함
STORE : 검수 대조·현금흐름 판단 후 세 갈래 응답 — ① payment-submitted (tx signature 첨부) ② negotiation-proposal (차감/유예/분할) ③ payment-refused (사유 + 에스컬레이션)
HQ : ①이면 온체인 검증 후 receipt 발행 · ②면 심사 후 수락/거절/역제안 (수락 시 조정된 payment-required 재전송 또는 예약 등록) · ③이면 분쟁 큐로 이동

참고 구현: github.com/google-agentic-commerce/a2a-x402 — 리소스 페이지에 주최측이 직접 링크한 레포.

04핵심 시나리오 3종 (= 데모 시나리오)

가맹점 3곳이 각각 하나씩 담당한다. A는 속도를, B는 지능을, C는 협상과 예약을 보여준다.

A지점 — 정상 플로우 즉시 자동 결제

sequenceDiagram
  participant W as Workflows
  participant HQ as 본사 에이전트
  participant A as A지점 에이전트
  participant S as Solana devnet
  W->>HQ: delivery.completed (A지점, 닭 100 · 야채 40)
  HQ->>A: x402 payment-required (35.0 USDC, memo=INV-001)
  A->>A: verify_delivery() → 검수 일치
  A->>A: assess_cashflow() → 잔액 충분 · 한도 내
  A->>S: USDC transfer 35.0 + memo
  A->>HQ: payment-submitted (tx sig)
  HQ->>S: verify_payment() — 금액·memo 대조
  HQ->>A: receipt (정산 확정)

B지점 — 검수 불일치 차감 협상

sequenceDiagram
  participant HQ as 본사 에이전트
  participant B as B지점 에이전트
  participant S as Solana devnet
  HQ->>B: payment-required (35.0 USDC, 닭 100 포함)
  B->>B: verify_delivery() → 닭 95만 입고 확인
  B->>HQ: negotiation-proposal (차감 −1.75, 근거: 검수 기록)
  HQ->>HQ: review_proposal() — 납품 로그 대조 → 수락
  HQ->>B: payment-required 재발행 (33.25 USDC)
  B->>S: USDC transfer 33.25
  B->>HQ: payment-submitted → receipt
  Note over HQ,B: 분쟁이 사람 없이 4턴 만에 종결

C지점 — 잔액 부족 유예 협상 + 예약 실행

sequenceDiagram
  participant HQ as 본사 에이전트
  participant C as C지점 에이전트
  participant SCH as Scheduler + Run Jobs
  participant S as Solana devnet
  HQ->>C: payment-required (35.0 USDC)
  C->>C: assess_cashflow() → 잔액 12 · 금요일 카드정산금 +80 예정
  C->>HQ: negotiation-proposal (금요일 전액 납부 유예)
  HQ->>HQ: review_proposal() — 신용점수 92 · 24회 연속 정시 납부 → 수락

  Note over SCH: (데모에선 시간을 당겨 실행)
  SCH->>C: 예약 트리거

  C->>HQ: payment-submitted → receipt · 신용점수 갱신
숨긴 카드 — 미발주 품목이 섞인 이상 청구를 주입하면 가맹점 에이전트가 refuse_payment()로 거부하고 사람에게 에스컬레이션. "에이전트가 돈을 아무 데나 쓰지 않는다"의 증명 장면.

05청구서 상태기계

청구서 하나의 생애. 모든 상태 전이는 events 로그와 1:1로 대응한다.

stateDiagram-v2
  [*] --> issued : 납품 이벤트 → 청구서 생성
  issued --> paid : 검수 일치 · 잔액 충분 → 즉시 결제
  issued --> disputed : 검수 불일치 → 차감 제안
  disputed --> issued : 조정 수락 → 재발행
  disputed --> escalated : 3턴 내 미합의
  issued --> scheduled : 유예/분할 수락 → 예약
  scheduled --> paid : 예약일 자동 실행
  scheduled --> escalated : 예약 실행 실패
  issued --> refused : 이상 청구 감지
  refused --> escalated : 사람 판단 대기
  paid --> settled : 온체인 검증 · 영수증 · BQ 기록
  settled --> [*]

06데이터 모델

상태는 Firestore, 이력은 BigQuery. 온체인 tx signature가 두 세계를 잇는 키.

Firestore 컬렉션주요 필드용도
storeswallet, credit_score, credit_limit, policy{auto_limit, defer_max_pct, installment_max}가맹점 프로필 + 에이전트 정책
invoicesstore_id, items[], amount, due_date, status, tx_sig청구서 (상태기계의 주체)
negotiationsinvoice_id, type(adjustment|deferral|installment), proposal, decision, reasoning협상 이력 — Gemini 판단 사유 포함
schedulesinvoice_id, execute_at, status예약 납부 (Scheduler가 소비)
eventsactor, action, payload, ts (append-only)실행 증빙 로그 — 심사 기준 4번

Payments Service API (payments/, 기존 골격 확장)

엔드포인트동작
GET /balance/:walletSOL·USDC 잔액 조회 (다중 지갑 지원으로 확장)
POST /payUSDC 전송 + memo(invoice_id) — 서명 지갑을 에이전트별로 분리
GET /tx/:sig트랜잭션 검증 (금액·수취인·memo 파싱) — HQ의 수금 검증용

BigQuery — settlement_history

청구·협상·결제의 최종 스냅샷을 append. 대시보드의 미수금 현황·지점별 신용점수 추이·평균 정산 소요시간이 여기서 나온다. "기존 30~60일 외상 정산 → 평균 N초"를 숫자로 보여주는 것이 발표의 결정타.
