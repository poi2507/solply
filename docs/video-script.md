**⚠️ 촬영 순서가 중요한 이유**: `solply-demo` Job(시나리오 A~F)은 DB를 리셋한다
(`--keep` 없이 실행 시). **라이브에 쌓인 기록(P2P 수십 건, 정산 이력)을 쓰는 장면 3을
반드시 먼저 찍고**, 그 다음 시나리오 장면(1·2·4)을 찍는다. 촬영이 끝나면 스케줄러를
재개 — 제출일(8/3)까지 3일이면 기록이 다시 수북이 쌓인다.

```bash
# ① 스케줄러 정지 — 촬영 중 상태가 바뀌지 않게
gcloud scheduler jobs pause solply-tick --location=us-central1

# ② 상태 점검
curl -s https://solply-api-965647250280.us-central1.run.app/api/shop | python3 -m json.tool | head -30
#    → 미달/품절 품목이 하나는 있어야 장면 3이 산다. 없으면 /shop에서 몇 개 사서 만든다.

# ③ (장면 3 직전) 시세 캐시 확인 — 마지막 틱 후 10분 지나야 시세 구매 장면이 확실히 나온다
#    (10분 안이면 캐시 재사용 = 구매 이벤트 없음. 정지 후 10분 기다리면 됨)

# ④ 시나리오 장면(1·2·4)용 — 전 시나리오 실행 (몇 분 걸림, 실행 중 화면도 B-roll로 녹화)
```

  잉여 → 남는 재고 · 유예 → 납부를 미뤄달라고 · 로그 → 기록 · 체인 → 블록체인 ·
  "정상 건" → "문제가 없으면" · **되제안 → 역제안(비표준어였음)**. USDC는 첫 등장에
  "달러에 연동된 코인인 유에스디씨"로 한 번 풀어준다. 숫자는 화면에 있으니 읽지 않는다.
- Explorer 컷은 1.5초면 충분 — "존재 확인"이 목적이지 읽히는 게 목적이 아니다.
- 장면 3의 시세 가격(수백 USD)은 **데모 제공자가 만들어 주는 난수**다 (같은 심볼이 몇 초 만에
  153 → 131로 바뀌고, 없는 심볼에도 값을 준다). 내레이션은 "데이터를 산다"에만 초점을 두고
  **가격 수치는 절대 언급하지 않는다.** 화면 문구는 `제공 pay.sh 데모 시세`로 나가므로
  심사위원이 스스로 데모임을 안다 — 숨기지 않는 게 안전하다.
- 만약 장면 3 틱에서 P2P 대신 본사 발주가 나오면 그것대로 찍는다 — "본사 발주 → 청구 → x402 결제"도 완결된 이야기다. 각본이 아니라 판단이라는 게 오히려 포인트.
