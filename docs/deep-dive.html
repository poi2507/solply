01

해결하려는 문제 — 외상 장부의 세계

치킨집 사장님과 본사 사이에 매일 오가는 돈, 그리고 그 돈이 왜 늘 시끄러운가

프랜차이즈 가맹점은 본사에서 식자재를 받아 쓰고, 값은 나중에 냅니다. 이 돈을 업계에서 물대(물품 대금)라고 부릅니다. 문제는 이 돈이 그냥 나가는 게 아니라 매번 네 가지 질문을 통과해야 한다는 겁니다.

① 진짜 왔나

청구서엔 닭 10마리인데 냉장고엔 9마리. 누가 맞나?

② 이거 시켰나

주문한 적 없는 바닷가재가 청구서에 있다.

③ 낼 돈 있나

지금 내면 다음 주 인건비가 모자란다.

④ 얼마나 미룰 수 있나

본사는 어디까지 봐줄까? 신용이 있으면 다를까?

지금은 이 네 질문을 사람이 전화와 엑셀로 처리합니다. 본사 정산팀 한 명이 수십 개 지점을 상대하고, 분쟁이 생기면 며칠씩 미뤄집니다. Solply는 이 일을 양쪽 에이전트가 서로 협상해서 끝내게 만든 시스템입니다.

비유

기존 방식은 단골 가게 외상 장부입니다. 주인과 손님이 서로 기억에 의존하고, 숫자가 안 맞으면 목소리 큰 쪽이 이깁니다.

Solply는 그 장부를 둘 다 못 지우는 공용 장부로 바꿉니다. 그게 블록체인이고, 그래서 "왜 온체인이어야 하는가"에 답할 수 있습니다 — 본사도 지점도 지난 기록을 고칠 수 없어야 협상이 성립하니까요.

왜 이 주제였나

해커톤 주제가 "AI 에이전트가 시작하는 상거래"였습니다. 챗봇이 아니라 돈이 실제로 오가는 유스케이스여야 했고, 그중에서도 (가) 반복적이고 (나) 금액이 또박또박 나뉘고 (다) 분쟁이 잦은 영역이 물대 정산이었습니다. 분쟁이 잦다는 건 단점이 아니라 에이전트가 협상할 거리가 있다는 뜻입니다.

04

x402 — 402 응답이 곧 협상 테이블

웹 표준의 빈 칸에 협상을 얹은 것이 이 프로젝트의 기술적 핵심

HTTP에는 402 Payment Required라는 상태 코드가 30년 넘게 비어 있었습니다. "돈을 내야 한다"는 뜻만 정해두고 어떻게 내는지는 정하지 않은 채로요. x402는 그 빈 칸을 채운 규약입니다.

비유

자판기를 생각해보세요. 버튼을 누르면 자판기가 "300원 넣으세요"라고 알려줍니다. 동전을 넣으면 물건이 나옵니다. 402는 그 "300원 넣으세요" 안내문의 웹 버전입니다.

그런데 우리 자판기는 특별합니다. 안내문에 선택지가 여러 개 붙어 있습니다 — "지금 300원" / "다음 주에 300원(신용 확인 필요)" / "150원씩 두 번". 이게 accepts[]입니다.

x402 표준은 accepts를 배열로 정의합니다. 원래 의도는 "USDC로도 받고 다른 토큰으로도 받는다" 같은 결제 수단 선택이었을 겁니다. 우리는 여기에 결제 조건(협상 옵션)을 담았습니다. 그래서 표준을 벗어나지 않고 협상을 표현할 수 있습니다.

왜 3중 대조인가

서명 하나만 확인하면 다른 청구서의 결제를 재사용할 수 있습니다. 그래서 셋을 봅니다 — ① 금액이 청구액과 같은가 ② 메모에 이 청구서 번호가 있는가 ③ 트랜잭션이 성공했는가. 솔라나 메모 프로그램에 청구서 번호를 새기는 게 이 대조의 핵심 고리입니다.

협상 시나리오 6종 — 데모가 보여주는 것

각 시나리오는 코드의 서로 다른 경로를 태운다

구분상황에이전트의 판단지나는 코드 경로
A 정상청구 = 입고즉시 결제verify → request_terms → cashflow → pay
B 차감10개 청구, 9개 입고차액 빼달라고 제안 → 본사 수락 → 재발행 후 결제verify → propose_adjustment ⇄ HQ review_adjustment → apply
C 유예잔액 부족입금 일정을 근거로 유예 요청 → 예약cashflow → propose_deferral ⇄ HQ review_deferral
D 거부발주 없는 바닷가재깎지 않고 거부 → 사람에게verify → refuse
E 직거래재고 부족, 옆 지점에 잉여본사 발주 대신 지점 간 거래 (본사 승인 필요)check_stock → find_supply → propose_trade ⇄ HQ review_p2p
F 분할전액 유예는 무리본사가 분할을 역제안 → 합의 → 회차별 결제HQ review_deferral(counter) → invoice.split

자율성의 경계 — 상한·하한·권한

함수 하나가 이 시스템의 신뢰를 떠받친다

비유

법인카드입니다. 신입에게 카드를 주되 "1회 10만원까지, 그 이상은 팀장 결재"라고 정합니다. 여기서 두 가지가 다릅니다 —

상한(auto_pay_limit)은 권한의 문제입니다. 돈이 있어도 신입이 정할 일이 아닙니다.
하한(min_reserve)은 능력의 문제입니다. 이걸 내면 다음 주 월급이 없습니다.

backend/app/agents/store/node.py — 순서가 곧 원칙 
def route_after_cashflow(state: StoreState) -> str:
    """상한(권한)을 먼저 보고, 그 다음 잔액과 하한(능력)을 본다.

    순서가 중요하다. 상한 초과는 "이 금액은 애초에 에이전트가 정할 문제가 아니다"라는
    권한의 문제라, 잔액이 넉넉하든 아니든 사람에게 간다.
    """
    if state.get("intent") == "invoice.pay_approved":
        return "pay"                                   # 사람이 이미 승인 → 권한 해소
    cash = state["cashflow"]
    if not cash.get("within_auto_limit", True):
        return "escalate"                              # ① 권한 — 사람에게
    if not cash.get("sufficient") or not cash.get("keeps_reserve", True):
        return "propose_deferral"                       # ② 능력 — 협상으로
    return "pay"

점주가 화면에서 설정하는 값들입니다. 코드에 하드코딩된 게 아닙니다:

정책기본값뜻
auto_pay_limit_usdc10이 금액까지는 사람 승인 없이 결제
min_reserve_usdc2결제 후 이 잔액 아래로 내려가면 결제 안 함

p2p_min_credit_score (본사)75직거래 참가 기준 — 즉시 결제라 여신이 없어 더 완만하다
기준을 두 개로 나눈 이유 (실제로 겪은 문제)

처음엔 신용 기준이 하나였습니다. 그래서 B지점(83점)이 직거래에서도 막혔습니다. 그런데 직거래는 즉시 온체인 결제라 본사가 떠안는 위험이 없습니다 — 유예(여신)와 같은 기준을 쓸 이유가 없었던 거죠. 그래서 p2p_min_credit_score를 따로 뺐습니다. 비즈니스 논리가 코드 구조를 바꾼 사례입니다.

품목이 하나(닭)일 때는 직거래가 "닭 하나 갖고 도는" 모양이었습니다. 지점마다 구색이 다르니 서로 다른 걸 주고받는 진짜 시장이 됩니다. 첫 틱에서 바로 B지점이 치킨무를 C지점에서 받아왔습니다.

하루가 밀리는 버그

처음 구현했을 때 오늘에서 이전을 누르면 7/29를 건너뛰고 7/28로 갔습니다. new Date("2026-07-30T00:00:00")는 로컬 시간으로 파싱되고 toISOString()은 UTC로 출력하는데, KST 브라우저에서는 이 둘의 차이가 9시간이라 날짜가 하루 밀립니다.
